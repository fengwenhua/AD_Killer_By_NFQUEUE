# KernelSU 软重启与守护生命周期

## 本次故障原因

2026-10-22 的设备记录显示：11:05:09 KernelSU 执行 `SoftReboot`，11:05:12 `netd` 重新启动。独立的旧 AD Killer 守护未退出，仍运行已被替换的 v1.2.2 映像，而安装文件已是 v1.2.3。

双栈 `ADK_NFQ_ENTRY` 都没有 OUTPUT 引用，队列依然绑定旧守护但没有新流量；指标的更新时间继续刷新，包数和拦截数不变。原启动脚本在 `autostart=false` 时立即退出，未处理软重启幸存的进程，因此出现“进程活着、路由失效”的半运行状态。

KernelSU 对应版本在停止 Android 用户态服务之前执行 `emulated-soft-reboot` 钩子，然后重新运行启动阶段。这给模块提供了先释放自身资源、再按策略启动的生命周期边界。[KernelSU 官方软重启实现](https://github.com/tiann/KernelSU/blob/46636100/userspace/ksud/src/soft_reboot.rs)

## v1.2.4 修复

- `emulated-soft-reboot.sh` 在用户态重启前调用 `--prepare-reboot`，只优雅停止已验证身份的本模块守护；由守护自己释放队列、路由和生命周期锁。
- `service.sh` 在判断自启策略前再次执行幂等清理，兼容从没有软重启钩子的旧包升级。无实例时不写配置、不创建数据目录、不清理防火墙。
- 生命周期停止不是用户暂停：不修改 `enabled`、`manual_stop`、`autostart`，不发 SIGKILL；退出超时则报错，启动脚本不再创建第二个实例。
- 开机自启关闭或用户已暂停，冷启动／软重启后均不启动。开启自启且未暂停，等待 `sys.boot_completed=1` 后才启动；等待超时或期间关闭开关则退出。
- `--status-fast` 读取双栈 OUTPUT，要求恰好一个稳定入口且没有旧式直接跳转；`route_check=entry` 不等同于完整链校验。`--status` 执行完整校验，两者均不再因查询而修改防火墙。
- 状态额外报告守护 PID 及 `daemon_image_current`，用文件身份判断正在运行的映像是否与查询二进制相同，不因 argv 路径相同就当作新版本。
- 概览轮询会把丢失入口或旧映像降级为可见提示，完整校验失败／不可读时不保持绿色；恢复正常也必须完整校验。页面不自动重启守护或插入路由。
- 用户点击“启动守护”时，即使旧路由仍健康，只要映像不同，也会优雅切换到当前二进制；继续保留超时保护和外部队列保护。

## 已安装旧版如何恢复

在 WebUI 点击“启动守护”可触发 v1.2.3 已有的缺失路由恢复逻辑，或先暂停再启动。不要手动往 OUTPUT 插一条跳转就算修复，否则旧映像和队列归属没有核实。

重启守护会重置“本次守护”统计，不删除规则、来源或应用名单。升级到修复版后，若自启关闭，软重启后手动启动属于预期行为。

## 验证边界

### 启停修订号与协调（O15）

`lifecycle.intent` 保存本次启动/暂停/生命周期停止的修订号。短时 `.intent.lock`
协调意图和策略；`.control.lock` 串行化实际启停、PID 发布及停止后置清理。
较新的请求取消尚未发布 PID 的旧请求；较旧 stop 若尚未进入操作阶段则被取消，
已进入清理阶段则完成清理，再允许新实例发布 PID。这两把协调锁等待有界，不持有
`.daemon.lock` 等待它所保护的守护退出；daemon 仅在 PID 发布前持有控制锁。

启动子进程必须携带与当前意图一致的修订号，在发布 PID 前再次确认策略。
单独设置 `ADK_NFQ_START_DISPATCHED=1` 或直接执行裸 `--daemon` 不能绕过暂停。
需要显式前台调试时使用 `--daemon --foreground`，它等同新的手动启动请求，
经过同样的预检和栅栏；不要把该选项用于开机自启。

`service.sh` 改用 `--start-boot`：后端复核自启开启且未暂停，不把开机请求
转换成手动恢复。加载期间关闭自启或暂停，也会在 PID 发布前失效。
`--prepare-reboot` 取消尚未启动的请求，但不修改 enabled/manual_stop/autostart。
没有数据目录时仍不创建目录；已有目录即使没有 PID，也需写入新的取消修订号。

普通主机多进程回归使用真实 CLI 控制流、意图文件、配置写入和文件锁，只有
PID 身份/cgroup/引擎/防火墙依赖被隔离；测试不等同于真实 Linux 内核路由竞态验证。
另外，`tests/integration/test_lifecycle_races.py` 在一次性 Linux 中只对 `nohup`
派发与 stop 后置清理工具加等待栅栏，执行真实 CLI、开机脚本、守护和双栈 NFQUEUE。
2026-10-23 已在 Debian arm64/Clang 14 的 nft、legacy 两套后端通过完整引擎集成，
覆盖派发后暂停、开机脚本与暂停、多窗口和旧清理/新启动，并实测新实例的 DNS
拦截/放行。没有把主机桩测试冒充这项内核证据，也没有据此声称手机已升级验收。

### 运行期冻结检查（O17）

`--status` / `--status-fast` 返回 `freezer_state=normal/frozen/unknown/not_running`。
`frozen=null` 表示未知，不等同于未冻结。`running=true` 仍可能只说明已确认的进程
存在；还须同时检查冻结状态、完整路由及映像，才能判断守护健康。
读取失败、缺少/损坏的冻结字段、仅子树挂载、观察期间退出/迁移/挂载变化均返回未知及
`freezer_error`；不会因未知而杀进程、迁移或解冻任何组。

WebUI 将未知显示为“状态未核实”，保持只读轮询并提供“重新核实状态”按钮；
只有完整检查通过才恢复绿色。未知期间不允许用“启动守护”触发自动替换，用户仍可
显式暂停。启动阶段原有的自迁移与迁移后确认仍然失败关闭，不放宽接管条件。

主机合成 I/O 与前端回归覆盖这些状态；不等同于本轮已在手机执行冻结/解冻试验。

主机／浏览器测试覆盖策略保持、超时、旧映像识别、入口缺失及界面恢复；一次性 Linux 内核测试覆盖真实队列、双栈路由和外部规则保留。真机恢复使用独立路由检查与计数增长，不以快速状态的旧版近似值代替证据。

没有为验证而对用户手机执行整机或软重启。其他管理器忽略 KernelSU 专用钩子，仍可由标准启动脚本完成旧实例清理。

在该 KernelSU 设备上，先备份原 v1.2.3 模块文件，再部署 [CI 39719108797](https://github.com/fengwenhua/AD_Killer_By_NFQUEUE/actions/runs/39719108797) 全部通过的 v1.2.4 **预览包**（versionCode `12400`，源码 `6db3424`）。包、校验文件、更新元数据和逐个已安装文件均已核验；没有改动 v1.2.3 正式发布。

- 新进程执行已安装的 v1.2.4 映像，`daemon_image_current=true`；完整与快速路由检查均通过，未被冻结。
- 实际执行模块的 `emulated-soft-reboot.sh`，确认守护退出、两个队列释放、模块双栈路由清理；再执行实际 `service.sh`，确认 `autostart=false` 时不重新启动。最后手动启动，恢复验收前的拦截状态。这里只验证模块钩子，**没有执行系统软重启**。
- 两个 NFQUEUE 的 netlink socket 均属于当前守护，积压、内核丢包、用户态丢包均为 0；双栈 OUTPUT 各有且仅有一个模块入口。
- 有界的本机回环探针实测如下；不访问外部广告站点。随后指标确认各有两次 DNS 否定应答、TCP reset、QUIC 快速拒绝；裁决、队列、过期裁决和响应失败计数均为 0。
