# 根管理器原生更新提示：调研与实现草案

调研日期：2026-10-22。本文只记录方案，本次不修改原生管理器适配、发布地址或发布流程，也不申请模块仓库上架。

## 结论：已有协议基础，先确认为什么没有提示

项目已经在 `module/module.prop` 声明：

```properties
updateJson=https://github.com/fengwenhua/AD_Killer_By_NFQUEUE/releases/latest/download/update.json
```

`scripts/release_metadata.py` 也已从实际 ZIP 生成标准字段。因此不是必须进入 WebUI 才具备检查更新的能力；应先验证手机已安装包里的声明、远端响应及管理器条件，不宜再造一套更新协议。[KernelSU 模块规范](https://kernelsu.org/guide/module.html#module-prop)、[Magisk 标准 Update JSON](https://topjohnwu.github.io/Magisk/guides.html#moduleprop)

管理器基本流程：读取已装 `module.prop` → 请求 `updateJson` → 比较构建序号 → 展示更新入口 → 用户确认下载、安装。

| 管理器 | 已核对的更新机制 | 需要单独验收的差异 |
| --- | --- | --- |
| KernelSU | 标准 `updateJson`、远端 `versionCode` 大于本地才返回更新 | 全局更新开关、模块状态、管理器缓存、不同版本的仓库校验 |
| APatch | 同类 JSON 与序号比较 | 版本、网络、模块启用及等待重启状态 |
| Magisk | 官方文档定义相同的四个标准字段 | 实际 App 版本、下载与安装体验 |

KernelSU 当前官方源码会跳过被禁用、待卸载、已处于更新等待状态，或没有更新地址的模块；其更新缓存也与模块信息及检查设置有关。APatch 的源码有相近的状态条件。具体行为应以用户实际安装的管理器版本为准，不把官方 `main` 的实现假定为所有分支都相同。[KernelSU 更新仓库逻辑](https://github.com/tiann/KernelSU/blob/main/manager/app/src/main/java/me/weishu/kernelsu/data/repository/ModuleRepositoryImpl.kt)、[KernelSU 缓存与检查入口](https://github.com/tiann/KernelSU/blob/main/manager/app/src/main/java/me/weishu/kernelsu/ui/viewmodel/ModuleViewModel.kt)、[APatch 更新逻辑](https://github.com/bmax121/APatch/blob/main/app/src/main/java/me/bmax/apatch/ui/viewmodel/APModuleViewModel.kt)

注意：在 AD Killer 概览里暂停守护，不等于在 KernelSU 中禁用整个模块。

## 当前不出现更新图标的排查顺序

1. 比较已装包和远端的 `versionCode`。例如两边都是 v1.2.2 / `12201`，不显示更新是正常结果；不要为了测试修改手机上的序号。
2. 只读检查已装模块的 `updateJson` 是否存在、是否是预期 URL；源代码有声明不等于手机旧包也有。
3. 确认模块未被管理器禁用、未待卸载、未处于等待重启的更新状态，并检查管理器的模块更新开关。
4. 从管理器实际使用的网络测试 HTTPS、GitHub 重定向、返回状态与内容。WebUI 使用 root 进程的下载路径，成功不代表管理器 App 的网络一定成功。
5. 对照管理器版本检查缓存行为；先使用正常刷新、重开管理器等入口，不直接清空整个管理器数据。

目前手机未连接 ADB，尚未取得本机管理器版本和上述网络证据；这里列的是排查条件，不是对该手机的根因结论。

## 拟实现方案（后续获准后再做）

优先保留现有稳定地址，统一由打包产物生成元数据，不维护第二套手填版本。结构示例，**不代表 v1.2.3 已发布**：

```json
{
  "version": "v1.2.3",
  "versionCode": 12301,
  "zipUrl": "https://github.com/fengwenhua/AD_Killer_By_NFQUEUE/releases/download/v1.2.3/AD_Killer_By_NFQUEUE-v1.2.3.zip",
  "changelog": "https://github.com/fengwenhua/AD_Killer_By_NFQUEUE/releases/download/v1.2.3/changelog.md"
}
```

- `version` 用于展示，判断先后靠严格递增的 int32 `versionCode`；正式构建必须高于对应预览构建。
- 管理器默认只发现正式版；WebUI 的“包含预览版”设置不应改变 KernelSU 等管理器的更新来源。
- 正式 ZIP、SHA-256、日志及 JSON 都上传、校验成功后，再设为正式 Latest，避免管理器先看到指向缺失附件的元数据。
- 确认标准四字段可被目标管理器解析；现有自有扩展字段不应成为管理器的依赖。不要宣称各管理器一定会验证项目自定义的 `sha256` 字段。
- 先用当前 GitHub 地址验收；只有证据确认管理器网络或重定向兼容性问题，才评估独立静态 manifest 地址，另外征求托管及迁移选择。
- WebUI 缓存只作用于本模块界面，不能替代管理器检查，也不能直接让管理器显示更新图标。

KernelSU 模块目录上架、托管 manifest 和仓库签名校验属于额外路线，不是本次直接启用的功能。若以后采用，需另行遵循其发布、不可变资产及序号规则。[KernelSU Modules 发布规范](https://developers.kernelsu.org/docs/releasing)

## 后续验收

- 使用真实的较低版本安装包和较高版本正式发布，在不打开 WebUI 的情况下，管理器刷新能显示更新入口。
- 同版本、较低版本、只有预览发布时不误报；同号预览转正式依靠更高构建序号识别。
- 断网、404、无效 JSON、错误版本类型、缺失 ZIP、GitHub 重定向失败不会误报可更新或安装成功。
- 验证 KernelSU、APatch、Magisk 的提示、更新日志、用户确认与等待重启体验；不得把本地 UI 测试当成三种管理器都已真机通过。
- 安装后保留规则、名单、默认策略及手动开关选择，重启后正确显示新版本。

本轮交付仅为此文档；现有 WebUI 更新与标准元数据生成逻辑保持独立。
