# 发布中断后的检查与恢复

普通 CI 仍只构建、测试，不发布。发布工作流仍要求指定全绿 main CI，不重新编译、不更换渠道、不覆盖公开标签或附件。新增恢复入口只补齐经核验的未公开草稿。

## 正常发布

在 **Actions → Publish immutable release → Run workflow** 填写 CI run ID、未使用的新版本和渠道，`operation` 选择 `publish`。其余恢复字段留空。

脚本核对原始 CI artifact 的 ID 和整体摘要，再核对其中四个文件的字节摘要。准备目录保存原始 `ci-artifact.zip`；发布前重新与 GitHub artifact 元数据及 CI 源码比对，不能只修改本地文件和 `manifest.json` 就更换产物。版本号和 versionCode 都必须高于已公开版本。

先创建草稿、上传四个附件并重新下载核验，再公开。正式版设为 Latest，预览版不设为 Latest；最后核对不可变状态、标签源码、附件地址和字节。成功状态为 `published_verified`。

工作流摘要包含 CI SHA/run ID、渠道、ZIP 等文件的摘要、原始 artifact 身份，以及 CI 配方声明的 NDK/API 和构建脚本/前端锁文件摘要。配方声明不是运行时工具链证明，也不是独立供应链签名。

## 上传中断：先 inspect

不要直接点击 **Re-run failed jobs** 或重复普通发布。工作流重跑保护和本地回执会阻止盲目重试；同版本已存在的草稿即使还没有标签，也会阻止新建。

1. 新开一次发布工作流，选择 `operation=inspect`，填写原 CI run ID、原版本和原渠道。
2. 已知草稿 ID 时填写 `draft_release_id`；不知道时留空，脚本只读列出同版本记录。没有记录不代表前一次请求一定没成功，不会因此自动创建；多个记录也不会自动选一个恢复。
3. 查看工作流摘要及 **AD-Killer-release-receipt-运行ID-尝试次数** artifact 中的 `release-state.json`、`manifest.json`。
4. 只有报告为 `draft_inspected`、`recoverable=true` 时，核对 Release ID、CI SHA、渠道、所有现存附件与原始 CI 字节、缺失附件列表，然后保存 `manifest_sha256`。

`prepare` 和 `inspect` 客户端主动拒绝写 API 与上传。检查现有公开版也是只读；可以确认原发布已完成，不会再 PATCH 或替换文件。历史正式版后来不再是 Latest 时，报告会明确记录 `latest=false`。

## 明确恢复同一草稿

核对报告后，新开工作流，选择 `operation=resume`，填写同一 CI run ID、版本、渠道，并提供报告中的 `draft_release_id` 和 `confirm_manifest`。确认值是整份产物身份的 SHA-256，来源、产物或渠道变了就必须重新检查。

恢复流程重新检查 CI、原始 artifact、源码、仓库设置和草稿身份，实际下载核对现存附件，只上传缺少的文件。不会删除、覆盖、重传已有文件，也不会新建另一个草稿。最后核验完整四件套，再公开一次。

下列情况会拒绝恢复：草稿已公开、源码/标题/说明/渠道变更、同版本存在多个草稿、标签指向不同源码、附件重复/损坏/尚未完成、原始 CI artifact 无法核实。保留现场，人工检查；无法证明同一来源和字节时应使用新版本，不能移动旧标签或重建公开发布绕过。

## 公开请求响应丢失

公开 PATCH 只发一次。超时、断连或响应异常之后，只通过 GET 有限读回核对，不再次发送公开请求。

| 回执状态 | 含义与下一步 |
| --- | --- |
| `draft_creation_unconfirmed` | 新建请求可能成功；只读查找同版本草稿，不能重复 POST。 |
| `draft_upload_interrupted` | 草稿及部分附件可能存在；先 inspect，再明确恢复。 |
| `publication_unconfirmed` | 公开状态尚不能确认；只读检查现有 Release。 |
| `published_pending_verification` | 已看到公开状态，但不可变、附件、标签或 Latest 尚未全部确认；只读复核，不能重发或替换。 |
| `published_verified` | 本次核验完成；不要重复发布。 |

读回最多 4 次，共用 45 秒预算；单次网络读另受不超过 10 秒的套接字超时约束。Receipt 在每个写请求前原子持久化；工作流结束时尽量保存报告，硬取消或 runner 丢失仍可能来不及上传。报告缺失、Actions 红色或接口超时均不能直接证明“尚未发布”。

仓库设置接口需要 Administration read 权限，普通工作流令牌可能不可读。明确读到关闭状态会在写入前中止；403/404 记为未核实，不冒充开启，保留原有 `KERNELSU_IMMUTABLE_RELEASES=enabled` 所有者确认，公开后仍必须读到 `immutable=true`。不增加令牌权限，也不要求长期私人 Token。接口权限与语义见 [GitHub 不可变设置 API](https://docs.github.com/en/rest/repos/repos#check-if-immutable-releases-are-enabled-for-a-repository)。

草稿附件通过授权的 [Release asset API](https://docs.github.com/en/rest/releases/assets#get-a-release-asset) 读取，重定向下载不携带 Authorization，且禁止 HTTPS 降级。草稿发现使用有权限的发布列表；[按标签查询接口](https://docs.github.com/en/rest/releases/releases#get-a-release-by-tag-name) 只保证查询已公开发布。

## 依赖维护

官方 Actions 已固定完整 SHA，审核记录位于 [actions.lock.json](../.github/actions.lock.json)，保留 Node.js 24；KernelSU 官方 Action 原有 SHA 不变。依据 [GitHub Action 固定依赖建议](https://docs.github.com/en/actions/reference/security/secure-use#using-third-party-actions)。

Dependabot 每周检查 Actions 和前端依赖，只提交 PR，不自动合并或发布。Action 更新需核对官方提交、`action.yml` 的 `runs.using` 和文件摘要，再更新锁记录；仅改工作流 SHA 会被契约检查拒绝。前端依赖继续保留准确版本与 package-lock；合并前仍须完整 CI。

## 本地入口与验证

在已有 `GITHUB_TOKEN` 环境下使用，GitHub Actions 会自动提供工作流令牌。以下 ID、版本和确认值均需替换为实际记录：

```sh
# 只读准备与检查已有版本，不创建草稿
python3 scripts/publish_release.py prepare --run-id 123456 --version v1.2.8 --channel stable --output dist/release-check --inspect-existing
python3 scripts/publish_release.py inspect --output dist/release-check

# 仅在核对 inspect 报告后，显式恢复指定草稿
python3 scripts/publish_release.py resume --output dist/release-check --release-id 123456 --confirm-manifest 报告中的SHA256

# 离线故障注入，不访问 GitHub、不发版
python3 tests/test_listing_and_release.py
python3 tests/test_release_transport.py
python3 tests/test_release_contract.py
```

已用强制只读客户端对现有 v1.2.7 原始 CI 产物及四个公开附件完成核验，结果为不可变且 Latest。该演练验证读取与校验，不等于真实上传/公开中断演练；本轮没有创建草稿、上传附件、发版或改变手机。
